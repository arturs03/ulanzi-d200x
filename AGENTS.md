# D200X Direct development

This is an independent Windows app, CLI diagnostic tool and per-user installer for the Ulanzi D200X. Keep profiles editable by any LLM through the documented JSON format; changing a profile must not require recompilation or an LLM API account.

## Stability requirement

Preview 17 widens the mapping inspector and makes fields use its available width. Monitor-backed temperature/GPU-load choices show the running-monitor/CSV-logging reminder beside Key type; CPU/RAM choices do not. Validate normal and compact layouts with the isolated UI checks. An open monitor without a CPU temperature sensor cannot supply that value; do not substitute CPU usage, historical readings or zero.

Preview 16 implements GPU Core load through the shared bounded CSV reader alongside CPU/GPU/hotspot temperatures. All GPU selections share one identity; load has an exact `/load/` sensor and percent unit. A saved GPU-load assignment may auto-match and save a unique load sensor on the configured GPU under owned cancellation. Diagnostics explain missing current-day/stale/sensor data without retry storms or restamping. The monitor remains a separate required source; this implementation does not authorize starting/configuring it automatically. Real values/resources/physical refresh remain pending.

Preview 15 follows the user's request to map temperature sensors automatically. New-source metadata may preselect only a unique CPU Package and unique GPU Core / GPU Hot Spot on one GPU. Ambiguous roles/GPUs require manual choices, saved selections/omissions are preserved, and no telemetry or monitor is started by metadata reading. This supersedes the earlier requirement to manually pick every unambiguous role; stale logs still supply names only.

Preview 13 fixes the reported System data collection stop: a deliberate read-only installed-provider probe reproduced a host minimum-interval exception after three nominal one-second readings. Windows timer rounding must cause a cancellable monotonic wait, not a fatal sampling error or faster acquisition. Cadence/validation/exchange remain serialized; failure diagnostics expose fixed host reasons and phase, never raw provider data or exception text. This CPU/RAM diagnosis is not real-temperature, USB or long-term stability evidence.

Preventing application failures, system crashes, black screens and BSODs is a core product requirement, explicitly reinforced on 2026-10-05. Favor stability over additional features. Never claim that user-space operation or passing automated checks guarantees that Windows, USB/GPU drivers or hardware cannot crash.

- Keep device interaction conservative: explicit display writes, cancellable I/O, stop on I/O failure/disconnection, no automatic retry/reconnect loops and no simultaneous Studio control.
- Avoid custom kernel drivers, firmware changes, direct hardware register access, GPU telemetry polling, elevation and Windows security changes. Any future need for those is a separate setup decision.
- Keep LLM customization inside validated declarative JSON profiles. Do not execute generated scripts or arbitrary command strings.
- Verify physical input before display transfers and actions, then assess repeated sessions and sleep/wake behavior. Do not mark the app stable based on compilation, UI rendering or a short successful run.

## Workflow

- Read README.md, docs/customization.md and profiles/profile.schema.json before changing public configuration.
- Build with ./build.ps1. Generate distributables with ./package.ps1. Use the existing .NET 8 SDK; do not add drivers or system dependencies.
- Root C# files implement HID/protocol/config validation and CLI checks. Desktop contains the WinForms app; Installer contains the setup app. out and releases are generated and ignored by Git.
- Device control starts stopped. Enable actions and Keep screen on default on per the user's preview 12 request; preserve user toggle choices on profile import. Actions require actual physical input while the controller is started. Keeping screens on starts with the controller, without requiring a prior page upload. Loading a profile may start assigned read-only providers, but must not launch mapped apps, send keys or write USB. Page transfers remain explicit.
- Preserve strict profile validation, native HID capability selection, concurrent-controller guards and the Studio-running check. Do not silently add shell/script actions, firmware writes, services or automatic startup.
- Installer operations are per user. Preserve profiles on update/uninstall. Validate fixed installation paths and reject directory links before removal. Never remove shared .NET caches or unrelated applications.
- Distinguish automated tests and app rendering from physical device verification.
